# PouchORM 5.1.1 safety release execution plan

Status: Complete

## Goal

Fix two related deletion bugs without adding a new user-facing concept:

1. A collection can currently delete a document owned by another collection
   when both collections share a database.
2. `onChangeDeleted()` is not called for a normal `remove()` because the
   deletion record loses its collection name.

PouchORM 5.1.0 is already published, so the next patch is 5.1.1.

## Simplicity constraint

This release keeps the existing PouchORM model intact:

- Keep `IModel`, `PouchModel`, `PouchCollection`, and `PouchORM`.
- Keep `upsert()`, `remove()`, `removeById()`, and `bulkRemove()`.
- Keep the existing method signatures and return values.
- Do not add a public error hierarchy, ownership API, configuration layer, or
  migration mechanism.
- Keep raw PouchDB access available through `collection.db`.

The fix belongs inside the existing deletion methods.

## Changes from the user's perspective

| Change                   | Before 5.1.1                                                                                                                    | From 5.1.1                                                                                                                                        |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Delete one document      | Passing a document from one collection to another collection's `remove()` can delete it when both collections share a database. | The deletion is rejected with a clear error and the document remains stored. Valid calls are unchanged.                                           |
| Delete several documents | `bulkRemove()` can include documents owned by another collection.                                                               | PouchORM checks collection ownership before submitting the batch. Valid batches retain their current result array and non-transactional behavior. |
| Observe deletion         | A normal `remove()` loses `$collectionType`, so the owning collection's `onChangeDeleted()` hook is skipped.                    | Deletions made through PouchORM retain enough metadata for the owning collection's hook to run.                                                   |

There is no application migration. Code using the collection that owns a
document continues to work. Code using one collection to delete another
collection's document begins failing because that behavior is unsafe.

## Implementation

### 1. Freeze the bugs with tests

- [x] Reproduce cross-collection deletion with two collections sharing one
      database.
- [x] Reproduce the missing `onChangeDeleted()` event.
- [x] Cover single, by-ID, and bulk deletion.
- [x] Confirm caller-owned objects are not mutated.

Acceptance: the new regression tests fail against 5.1.0 for the expected
reasons.

### 2. Add one internal ownership check

- [x] Before deleting, read the current stored document by ID.
- [x] Compare its stored `$collectionType` with the collection performing the
      deletion.
- [x] Reject a mismatch with a concise error that names the document and
      expected collection.
- [x] Reuse the same internal check from `remove()` and `bulkRemove()`.
- [x] Continue using the caller's revision so stale writes still produce the
      normal PouchDB conflict.

Acceptance: no public collection deletion method can delete a document that is
stored under another collection.

### 3. Preserve deletion routing

- [x] Write deletions as cloned tombstones that retain `$collectionType`
      instead of using the metadata-stripping `db.remove(id, revision)` path.
- [x] Route the resulting change only to the owning collection.
- [x] Verify the hook runs once for valid single, by-ID, and bulk deletions.
- [x] Verify a non-owning collection receives no hook.

Acceptance: deletions performed through PouchORM invoke the existing
`onChangeDeleted()` hook without changing the hook API.

PouchORM cannot reliably route a deletion created by an old client or direct
PouchDB call when its tombstone contains no collection name. It must ignore
that event rather than guess.

### 4. Document and verify

- [x] Update the writes and API documentation with the ownership behavior and
      deletion-hook limitation.
- [x] Clarify that direct `collection.db` calls bypass PouchORM behavior.
- [x] Add a concise 5.1.1 changelog entry.
- [x] Run the full repository verification suite.
- [x] Exercise valid and rejected deletion through the packed npm package.
- [x] Build the documentation site.

Acceptance: tests, declarations, examples, the packed consumer, and
documentation build all pass.

### 5. Release

- [x] Set the package and lockfile version to 5.1.1.
- [x] Open and review one focused pull request.
- [x] Merge only after CI and documentation checks pass.
- [x] Publish `pouchorm@5.1.1`.
- [x] Install 5.1.1 from the public npm registry and repeat the valid and
      rejected deletion checks.
- [x] Create the matching GitHub release.
- [x] Verify the updated documentation at its public HTTPS URL on desktop and
      mobile.

Acceptance: npm, GitHub, and the public documentation expose the verified
5.1.1 release.

## Not part of this release

- Model renaming or replacement types such as `PouchEntity`, `Saved<T>`,
  `New<T>`, or `Patch<T>`.
- New write methods or changed conflict behavior.
- A schema or migration system.
- A synchronization abstraction.
- Reactive queries, framework bindings, or developer tools.
- ESM conversion or PouchDB packaging changes.

These ideas require separate evidence that they improve PouchORM without
weakening its simplicity.

## Replay notes

- Setup and verification: `npm ci`, then `npm run verify`.
- Documentation: `npm --prefix website ci`, then
  `npm --prefix website run build`.
- Tests use the in-memory PouchDB adapter.
- The release smoke test uses a clean temporary project and the exact package
  from the npm registry.
- No design brief is required because this patch has no visual interface.
- Definition of done: the ownership and deletion-hook checks pass through the
  public package, and the public documentation has been directly verified.
